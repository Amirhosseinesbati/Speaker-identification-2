# سیاست استفادهٔ مجدد از شواهد اعتبارسنجی

## هدف

اعتبارسنجی عمیق باید به یک **هویت فنی مشخص** متصل باشد، نه به هر اجرای
آموزش. تا وقتی این هویت تغییر نکرده است، شواهد قبلی دوباره استفاده می‌شوند تا
زمان GPU و هزینهٔ اجرای آزمایش صرف اسکن‌های تکراری نشود. این سیاست جای ارزیابی
علمی هر candidate را نمی‌گیرد: هر candidate همچنان باید metricهای OOF، gates و
parity لازم برای promotion را بگذراند.

## مبنای فعلی

برای هویت فعلی، ممیزی عمیق زیرساخت و داده پیش‌تر با موفقیت انجام شده است؛
runtime آموزش روی RTX 3090 قابل استفاده بوده، F005 تا انتها اجرا شده و run
ثبت‌شدهٔ آن در MLflow وضعیت نهایی دارد. این موارد شاهد سلامت مبنا هستند، نه
تضمین کیفیت candidateهای بعدی.

## tuple هویت ممیزی

رسید ممیزی باید این tuple را ثبت کند:

1. **کد:** Git commit و hash قطعی snapshot منبع.
2. **پروتکل:** hash تنظیمات حل‌شده، split/fold، seed، crop، scorer و سیاست انتخاب/کالیبراسیون.
3. **داده:** hashهای manifest، roles و label map، تعداد فایل‌های مورد انتظار و هویت canonical محتوا.
4. **مدل:** معماری/frontend و hash وزن پایه یا checkpoint مبدأ.
5. **runtime:** Python، نسخه‌های اصلی، CUDA/torch و کلاس GPU.

دو اجرا فقط وقتی یک مبنای قابل‌استفاده دارند که اجزای مرتبط tuple برابر باشند و رسید قبلی کامل و بدون خطای حل‌نشده باشد.

## شرایط استفادهٔ مجدد

با tuple یکسان، اجرای جدید از نتیجهٔ ممیزی عمیق قبلی استفاده می‌کند. در این حالت پیش از یک گروه اجرای همگن، فقط کنترل‌های سریع زیر انجام می‌شوند:

- تطابق commit، config و hashهای هویت با رسید مبنا؛
- وجود فایل‌ها و مسیرهای لازم، ظرفیت دیسک و نبود resume ناسازگار؛
- import مختصر runtime، دیده‌شدن CUDA/GPU و smoke forward قطعی در صورت شروع session تازه؛
- قابل‌نوشتن‌بودن spool و round-trip سبک MLflow فقط در شروع batch یا پس از خطای ارتباط.

بازوی هم‌هویت بعدی همان batch، این کنترل‌ها را دوباره تکرار نمی‌کند.

## چه چیزی ممیزی را باطل می‌کند

| تغییر مشاهده‌شده | اقدام لازم |
|---|---|
| commit، source snapshot، config حل‌شده یا پروتکل تغییر کند | آزمون و ممیزی هدفمند کد/پروتکل؛ اسکن کامل داده و پکیج لازم نیست. |
| manifest، roles، labels، مجموعهٔ فایل‌ها، محل استخراج یا هویت archive تغییر کند | ممیزی دوبارهٔ هویت داده. |
| وزن مبدأ، معماری، frontend یا مسیر scoring تغییر کند | بررسی یکپارچگی مدل، forward و parity مرتبط. |
| venv بازسازی شود، نسخه‌های اصلی، CUDA/driver یا سرور/GPU عوض شود | ممیزی دوبارهٔ runtime شامل dependency، decode واقعی و forward واقعی. |
| فقط reboot یا session تازه رخ دهد و tuple runtime ثابت بماند | کنترل سریع runtime کافی است. |
| binding/endpoint MLflow ناسازگار یا ارتباط آن قطع شود | فقط round-trip و spool MLflow دوباره بررسی می‌شود. |
| رسید ناقص، hash ناسازگار یا خطای صحت حل‌نشده دیده شود | بخش مرتبط ممیزی دوباره انجام می‌شود و آموزش شروع نمی‌شود. |

## کارهایی که تکرار نمی‌شوند

در نبود invalidator، اجرای جدید نباید CRC/SHA همهٔ صوت‌ها، اسکن کامل source، بازسازی dependency graph، `pip check` کامل، decode گسترده، دانلود دوبارهٔ archive یا forward/CPU-CUDA فراگیر را تکرار کند. parity دقیق و ممیزی کامل فقط برای تغییرهای مؤثر بالا یا candidateی که به مرحلهٔ promotion رسیده است انجام می‌شود.

## چرخهٔ عملی

1. receipt مبنا خوانده و tuple جدید با آن مقایسه می‌شود.
2. در صورت تطابق، کنترل سریع یک‌بار برای batch انجام و اجرای آزمایش آغاز می‌شود.
3. در صورت تفاوت، تنها لایهٔ باطل‌شده بازبینی می‌شود.
4. نتیجهٔ reuse یا invalidation همراه با tuple و علت در MLflow ثبت می‌شود؛ بدون صوت خام، وزن، cache یا credential.
